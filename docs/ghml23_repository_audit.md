# GHML23 repository classification audit

Checked all repositories 2026-10-01 against each public GitHub repository page: description, topics, README, and relevant linked project documentation. The 120 repository names and GHML23 source categories remain the published source snapshot. The adapted decisions and taxonomy labels classify each repository’s own current contribution under `config/prompts/github.toml` and `config/taxonomy/github_system_types.toml`. Traffic analyzers and all 13 previously flow-tagged repositories were checked again on 2026-10-02, following official documentation and source configurations. Packet, endpoint, service-log, and enforcement boundaries were rechecked on 2026-10-02. GitHub repositories can change after this review.

`unknown` means the available evidence does not support a configured system type. `uncertain` means the repository-level evidence no longer supports a reliable role. Repository descriptions are evidence leads, not proof of every fine-grained label; classification rationales and source URLs for the boundary review are in `annotation_note` and `annotation_sources` in the TOML profile.

Additional first-party evidence used for disputed labels: [Kismet WIDS alerts](https://www.kismetwireless.net/docs/readme/alerts/alerts/), [ntopng alerts](https://www.ntop.org/guides/ntopng/basic_concepts/alerts.html), [Velociraptor Sigma evaluator](https://docs.velociraptor.app/docs/troubleshooting/debugging/global/vql/plugins/sigma/), [Velociraptor process termination](https://docs.velociraptor.app/vql_reference/other/pskill/). Network quarantine alone no longer establishes HIPS.

## Traffic-analysis and flow-input follow-up (2026-10-02)

The `traffic_analyzer` role and `NSM` type represent executable security traffic analysis whose principal function is inspection, telemetry, or investigation. They apply here to **Zeek, Arkime, Joy, Mercury, and Dshell**. Limited checks and programmable detection policies can coexist with this role. Zeek does ship detection policies and a notice framework: the distinction is its principal function and operator-selected actionable policy, not the absence of every built-in detection. See [Zeek's own description](https://docs.zeek.org/en/current/about/what.html) and [notice policy documentation](https://docs.zeek.org/en/current/scripts/base/frameworks/notice/main.zeek.html). Protocol decoding by itself is neither a detection method nor evidence of PIDS. Traffic analyzers remain outside the operational-detector reporting segment.

`flow_analysis` now requires an implemented path that **reads aggregated flow/session records**, including CSV, JSON, TSV, or NetFlow/IPFIX records. PCAP/live packet input, internal stream reconstruction, and exported flow records alone support `packet_analysis`. A separate component that queries stored session summaries does support `flow_analysis`. Log and flow labels can both apply when the log contains aggregated connection records. Individual protocol events or endpoint network events do not automatically qualify.

All **13 previously flow-tagged repositories** were rechecked. Seven retain the label; six lose it. Arkime also gains it because its separately runnable Viewer analyzes stored session records.

## Non-network and mixed-source security monitoring (2026-10-02)

## Packet inspection, endpoint activity, and enforcement boundaries (2026-10-02)

These are the catalogue's operational definitions. System type depends on the implemented detection path and enforcement target. Deployment on a host, forwarding to a manager, a log filename, or NDR/EDR branding alone does not decide the type.

| Type | Required detection path | Additional requirement for prevention |
| --- | --- | --- |
| NIDS / NIPS | Intrusion inspection of packets or protocol streams from interfaces, taps, or saved packet captures, including a material integrated packet detector. | NIPS enforces network prevention through packet drops/rejects or firewall changes. |
| HIDS / HIPS | Endpoint process, file, execution, syscall, account, registry, or OS audit activity/state, including corresponding logs forwarded to a manager. | HIPS enforces endpoint protection, such as process termination, execution restrictions, file quarantine, persistence removal, or account disablement. |
| IDS / IPS | General detection, including network-service logs, authentication failures, aggregate-flow records, or application connection-policy events without a NIDS/HIDS detection path; also insufficiently specified subtypes. | IPS implements prevention. Log-derived source-IP bans and application connection-policy enforcement qualify here. |

Firewall-only blocking and network isolation do not establish HIPS. Packet interception for application connection permissions alone does not establish NIPS; a genuine packet intrusion engine remains NIDS/NIPS even when deployed on one host. Aggregated records read from an external packet analyzer do not make the consumer a packet detector. General IDS/IPS labels are not automatically added as parents of every specific type; a separately evidenced general path can justify them alongside another type. The configured definitions are injected into the final classification prompt, and the keyword/NLI baselines and default schema descriptions have also been updated. Keyword baselines remain lexical approximations and cannot prove these semantic distinctions.

## Antivirus and malware file scanning (2026-10-02)

The `antivirus` role describes a runnable system whose principal contribution scans files, uploads, binaries, archives, or cloud-storage objects for malware. The `AV` type records that function, and `file_analysis` records its evidence input. Signature, hash, IOC, YARA, heuristic, and learned-model approaches may qualify. Live activity monitoring and a repository-owned scanning engine are not required: on-demand scans and services integrating external engines qualify. Merely integrating several antivirus engines does not make a principal file-scanning service an IDS platform. File scanning, upload rejection, and malware quarantine alone do not establish HIDS/HIPS/APIDS. File-integrity monitoring against a trusted baseline and behavioral intrusion detection remain distinct.
